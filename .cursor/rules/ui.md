# Heroes 5 Mod: In-Game UI Guide

## Overview

The game UI is entirely data-driven: every window, button, text view and texture is an XML `.xdb` file. The mod touches the UI in two places:

- **The in-game encyclopedia ("Doc")**: a custom window opened from the adventure map and the lobby screens. It documents heroes, skills, artifacts and creatures. It lives in the `game_data/www*` folders. Much of it is generated by Python + Jinja2 scripts in `tools/generators/`.
- **Overrides of vanilla screens**: these are files that replace the game's own UI files at the same path, for example the combat stack info or the level-up box. Most of them are in `game_data/hud/UI/`. A few that hook the encyclopedia into vanilla screens are in `game_data/www/UI/` and `game_data/www-skills/UI/LevelUpBox/`.

### Data folders and paks

| Folder | Pak | Content |
|--------|-----|---------|
| `game_data/www` | `h5x-www.pak` | Encyclopedia root window, tabs, open/close buttons, Summary tab, shared textures, creature count numbers (`UI/Doc/Common/N/`), and the vanilla screens patched to host the encyclopedia |
| `game_data/www-heroes` | `h5x-www-heroes.pak` | Heroes tab (`UI/Doc/Heroes/`) |
| `game_data/www-skills` | `h5x-www-skills.pak` | Skills tab (`UI/Doc/Skills/`) and the patched level-up box (`UI/LevelUpBox/`) |
| `game_data/www-artifacts` | `h5x-www-artifacts.pak` | Artifacts tab (`UI/Doc/Artifacts/`) |
| `game_data/www-creatures` | `h5x-www-creatures.pak` | Creatures tab (`UI/Doc/Creatures/`): side-by-side comparison of two creatures, not yet tested in game |
| `game_data/hud` | `h5x-hud.pak` | Overrides of vanilla UI screens and textures |

The content of each folder is zipped from its root, so `game_data/www-heroes/UI/Doc/Heroes/...` becomes `/UI/Doc/Heroes/...` in the game's virtual file system. The game merges all paks into **one virtual file system**, which has these consequences:

- A file in one pak can reference a file in another pak. For example, `www/UI/Doc/Root.(WindowSimpleShared).xdb` references `Heroes/Heroes.(WindowSimple).xdb`, and that file is shipped by `www-heroes`.
- The same path must never exist in two folders. `tools/release.py` packs every folder into a single pak, so a duplicate path would collide.
- When a change spans several folders, sync every pak involved.

Sync scripts must be run from the `tools/` folder. They use the `H5_Folder` environment variable as the game path when it is set:

```powershell
./sync-www.ps1            # game_data/www
./sync-www-heroes.ps1     # game_data/www-heroes
./sync-www-skills.ps1     # game_data/www-skills
./sync-www-artifacts.ps1  # game_data/www-artifacts
./sync-www-creatures.ps1  # game_data/www-creatures
./sync-hud.ps1            # game_data/hud
```

## XDB UI file anatomy

### File naming and references

- The file name pattern is `<Name>.(<Type>).xdb`, for example `Alaric.(WindowMSButton).xdb`. Textures are split into a `.dds` image and a `(Texture).xdb` descriptor.
- References use `href="<path>#xpointer(/<RootElement>)"`, for example `href="Close.(WindowMSButton).xdb#xpointer(/WindowMSButton)"`. Text files are referenced without an xpointer: `href="/Text/Game/Heroes/Persons/Haven/Alaric/Name.txt"`. **A texture needs its xpointer** (`.../Active.(Texture).xdb#xpointer(/Texture)`): without it, the game draws a white square, even though the texture exists (the Creatures side buttons and resource icons did).
- Paths are either **relative to the referencing file's folder** (`army/Alaric_army.(WindowSimple).xdb`) or **absolute from the virtual root** (`/UI/Doc/Heroes/Common/HeroSpec.(TextFormat).xdb`). Use absolute paths for shared or cross-pak resources, and relative paths inside one component's folder.
- An empty reference is written `<Tag/>` or `href=""`.

### Instance and Shared files

Most UI elements come as a pair:

- **Instance** (`WindowSimple`, `WindowMSButton`, `WindowTextView`, ...): this file holds the element's identity and per-instance data. It contains `<Name>`, `<Visible>`, `<Priority>`, the tooltip, the placement override, `<GameMessageReactions>`, and for buttons the `<ButtonStates>`. It points to its Shared file with `<Shared href=...>`.
- **Shared** (`WindowSimpleShared`, `WindowMSButtonShared`, `WindowTextViewShared`, ...): this file holds what instances can share. It contains `<Children>` (the child elements, listed as instance hrefs), `<Background>`, `<Foreground>`, the default `<Placement>`, and for buttons the `<VisualStates>`.

A window's children are declared in its **Shared** file. To add an element to a window, add an `<Item href=...>` to that window's Shared `<Children>`. Several instances can reuse the same Shared file. For example, every creature slot uses `/UI/Doc/Heroes/_Creatures/<CREATURE>.(WindowSimpleShared).xdb`.

### Placement

```xml
<Placement>
  <Position><First><x>50</x><y>50</y></First><Second>true</Second></Position>
  <VerAllign><First>EPA_LOW_END</First><Second>false</Second></VerAllign>
  <HorAllign><First>EPA_LOW_END</First><Second>false</Second></HorAllign>
  <Size><First><x>0</x><y>0</y></First><Second>false</Second></Size>
  <LowerMargin>...</LowerMargin>
  <UpperMargin>...</UpperMargin>
</Placement>
```

- Each field is a `First` (the value) / `Second` (a boolean that says whether this file sets the value) pair. In an instance, `Second=false` means the value comes from the Shared file.
- Coordinates are in pixels, relative to the parent window. The encyclopedia root is laid out on a 1280x1024 canvas.
- `EPA_LOW_END` anchors to the top or left edge, and `EPA_HIGH_END` anchors to the bottom or right edge. With `EPA_HIGH_END`, negative positions move the element inwards. For example, `Doc/Open` sits at `-131,-151` from the bottom-right corner.
- `ERA_CENTER` centers the window, by its size, on its parent, and the position then offsets it. In the level-up dialog (1024x768), `ButtonOk` (`167,243`) and `Skill1` (`-103,76`) are placed by their centers, and `LevelUpBoxBg` (526x630) is centered by its shared position `0,0` (its own `-263,-315` has `Second=false`, so it is ignored).
- `Priority` sets the drawing order. Higher values are drawn on top. **Give a text a higher priority than its backdrop.** With equal priorities, the backdrop hides the text, even when it is listed first in `<Children>`. Working pairs: the skills description list (9999) over `DescriptionBack` (100), and a hero spec text (100) over `HeroSpecBack` (0).

### Known types and ClassTypeIDs

Instance files contain a `<ClassTypeID>` that the engine needs. Shared files have none. When you create a file by hand, copy the ClassTypeID from an existing file of the same type:

| Type | ClassTypeID | Purpose |
|------|-------------|---------|
| `WindowSimple` | 285700801 | Container window (panel, tab content, icon holder) |
| `WindowMSButton` | 285694855 | Multi-state button (tabs, hero list, skill icons) |
| `WindowTextView` | 285694860 | Text block bound to a `.txt` file |
| `WindowStaticText` | 554818304 | Static label (vanilla level-up box) |
| `UISSendUIMessage` | 285694982 | Command that shows, hides, enables or disables a window by name |
| `UISDirectRunReaction` | 554457792 | Command that runs an adventure reaction (used to broadcast a game message) |
| `ARSendGameMessage` | 352859136 | Reaction that broadcasts a named game message |
| `BackgroundSimpleScallingTexture` | 285694784 | Texture stretched to a size (icons, portraits) |
| `BackgroundSimpleTexture` | 285694785 | Texture at its native size (button states, highlights) |
| `ForegroundTextString` | 285694787 | Text drawn over a window (creature counts) |
| `TextFormat` | 387292225 | Text layout that wraps a format string (`FormatStringFileRef`) |

`ObjectRecordID` values are copied from the original files and are not unique in the repo. Keep them as they are and do not try to renumber them.

## Interactivity

### Showing and hiding windows

Windows are toggled by **name**, using `UISSendUIMessage` commands:

```xml
<UISSendUIMessage ObjectRecordID="5">
  <ClassTypeID>285694982</ClassTypeID>
  <SUIStateBaseFakeField>0</SUIStateBaseFakeField>
  <szMessageID><First>UI_SHOW_WINDOW</First><Second>true</Second></szMessageID>
  <szParam><First>WindowAlaric</First><Second>true</Second></szParam>   <!-- target <Name> -->
  <nForwardParam><First>1</First><Second>true</Second></nForwardParam>  <!-- value when run -->
  <nBackParam><First>0</First><Second>true</Second></nBackParam>        <!-- value when reversed -->
</UISSendUIMessage>
```

- The message is `UI_SHOW_WINDOW` (1 = show, 0 = hide) or `UI_ENABLE_WINDOW` (1 = enable, 0 = disable).
- `szParam` must match the `<Name>` of the target instance exactly. **Window names are global.** Keep them unique across all paks by following the naming conventions: `Window<HeroID>`, `Button<HeroID>`, `Window<SkillUID>`, `DocSkillsSelection<SkillUID><variant>`, `DocHeroes<Faction>`, and so on.
- Toggled windows start with `<Visible>false</Visible>`.
- The usual pattern is a pair of message files, `SwitchOn` and `SwitchOff` (or `<X>Show` and `<X>Hide`), stored next to the window they control.

### Buttons

- The instance's `<ButtonStates>` holds one `<Item>` per logical state. Each state has `CommandsOnEnterState`, `CommandsOnRightClick` and `commandsOnLDblKlick`.
- The Shared file's `<VisualStates>` holds one `<Item>` per state. Each one has the sub-states `Normal`, `MouseOver`, `Pushed`, `Disabled` and `RightButtonDown`, each with its own `Background`, `Foreground` and `OnEnterSubState` commands. It also has `VisualOnEnterState` commands that run when the button enters that state.
- **Toggle buttons** (hero and artifact buttons) have two states. Entering state 1 runs the commands that show its content and hide the other contents. Entering state 0 runs the commands that hide its content.
- `ButtonGroupID` groups buttons that act together. The Heroes faction buttons use `1` and hero buttons use `12`, so that selecting one releases the others. Artifact view buttons use `20` and category buttons `21`. The Skills faction buttons have no group (see the level-up box). **No button with a group may be part of a dialog**: see the level-up box.
- **Text buttons**: a button can show a text instead of a texture. The instance sets `<TextFileRef>`, and each sub-state of the Shared file sets a `<TextFormat>`. This is how vanilla `/UI/Common/MenuButton` works. The Artifacts tab uses it, changing the text color per sub-state.
- **Hover effects**: put commands in a sub-state's `OnEnterSubState`. Skill icons use `MouseOver` to highlight their prerequisites and to show the description panel.
- `TriggerMode` is `BCST_ON_PUSH` for the toggle buttons (factions, heroes, artifact views and categories) and `BCST_ON_RELEASE` for the others (encyclopedia tabs, skill icons, the encyclopedia Open button, the skills view buttons).
- **A button's state can't be set by a command.** Only `UI_SHOW_WINDOW` and `UI_ENABLE_WINDOW` exist. To show which of several click buttons is selected, disable the selected one with `UI_ENABLE_WINDOW`: its `Disabled` sub-state draws the "selected" look, and it can't be clicked again. The skills view buttons (Might/Magic) and the skill selection highlights of the old trees work this way. **Don't use it on a button with `MouseOver` commands**, such as a skill showing its description: a disabled button never reverses them, so the description stays shown. Show the selection with a separate window instead, as the build layout does.
- **Click buttons** have a single state. Their commands are in the instance's `CommandsOnEnterState`, with `AutoChangeState` set to `false` and `ButtonGroupID` set to `0`, like `www/UI/Doc/Open`.
- **A clickable button draws its icon as the `Background` of each sub-state**, like the skills view buttons. An icon window among the button's `<Children>` catches the clicks: the button is still hovered, but it can't be clicked. The skill tree icons have such a child, which is fine only because they're never clicked.

### Broadcasting a game message

A button can broadcast a message that many windows react to, without referencing each of them. The former skill trees reset all their highlights this way (in `www-skills/UI/Doc/Skills/`, no longer used):

1. `Common/HideAll.(UISDirectRunReaction).xdb` sets `ReactionForward` to `HideAll.(ARSendGameMessage).xdb`.
2. `HideAll.(ARSendGameMessage).xdb` sets `<EventName>DocSkillsHideAll</EventName>`.
3. Every reacting window declares that message in `<GameMessageReactions><Item><GameMessage>DocSkillsHideAll</GameMessage><VisualReaction><Commands>...`.

## Texts in the UI

- **Translatable texts** (names, descriptions, tooltips) are referenced from `game_texts/texts-<LANG>/` through absolute paths like `/Text/...` or `/GameMechanics/RefTables/...`. Generators read these paths from the mechanics data, so they stay in sync. See `text.md` for the format and the tags.
- **UI-local texts** (tab tooltips, labels, format strings) are `.txt` files placed next to the `.xdb` files in `game_data/www*`, for example `UI/Doc/DocTabHeroes.txt`. They are UTF-16 LE, they are **not translated**, and they belong to the data pak.
- **Text styling**: a `WindowTextView` points to a `TextFormat`, which points to a `FormatStringFileRef` `.txt` file. That file contains formatting tags such as `<h2>`. Reuse the existing formats in `UI/Doc/Heroes/Common/` and `UI/Doc/Skills/Common/`.
- **Numbers**: creature counts are displayed with `ForegroundTextString` files that reference `/UI/Doc/Common/N/<n>.txt`. The heroes generator creates the missing number files in `game_data/www`, so sync `www` as well when new counts appear.

## Encyclopedia structure

### Entry points

- **Adventure map**: `www/UI/AdventureScreen-Heavy.(WindowScreenShared).xdb` adds `Doc/Root.(WindowSimple).xdb` and the `Doc/Open` button. That button runs `zDocOpen`, which sends `UI_SHOW_WINDOW` to `DocRootWindow`.
- **Lobby and wait screens** (`CustomGameWait`, `HotSeatWait`, `MPWait`): these add `Doc/Root` and `CustomGameWait/OpenDoc`.
- **Level-up box**: `www-skills/UI/LevelUpBox/` overrides the vanilla level-up dialog (`AdventureDialog`). The dialog isn't part of the adventure screen (the engine creates it), so the adventure screen's encyclopedia opens behind it and can't be used. The dialog has its own encyclopedia root as a child, `LevelUpBox/DocRoot` (`DocRootWindowLvUp`): its Shared lists only the Skills section of `Doc/Root` (no tabs), through an absolute href, with its own Close button (`Buttons/DocClose`, `DocCloseLvUp`). The engine centers the 1024x768 dialog on the screen, and only that area takes clicks, so the root (1280x1024) is centered on the dialog (`ERA_CENTER`) and offset by 88,154, which puts its top-left corner at -552,-358 from the dialog's center (the encyclopedia spans x 40..1082 and y 0..717 of the root). A position of -552,-358 put most of it off the screen, up and to the left rather than placed like the adventure screen's root (then at 50,50 of the screen); at that place its Close button was out of the clickable area. Its name must differ from `DocRootWindow`: with the same name, the show message reached the adventure screen's root. Its `Buttons/OpenDoc` button (`DocOpenLvUp`, 32x32, centered at -63,231 from the dialog's center, with its own Shared and textures: `Buttons/Passive`, and `Buttons/Pressed` when pushed) shows it and its Skills section (`SkillsShow`), on the last selected faction. The section inside keeps the names of the adventure screen's one. **Loading a save made after opening it crashed** (`0x00A4E002`, eax = 0). The adventure screen (`CWindowScreen`) keeps a list of the button groups of its windows, as (`ButtonGroupID`, parent window) pairs. The dialog's buttons with a non-zero `ButtonGroupID` (Skills and Heroes faction buttons: 1, hero buttons: 12, artifact views: 20 and 21) add their parents to that list, and the entries outlive the dialog. The save writes those dead windows as released objects (flag 0 in its object table), the load re-creates them as empty `CWindowSimple` (no parent, no DB instance, no Shared), and the layout pass of the screen's activation reads their Shared size (`FUN_00A4DFF0`, through `FUN_00488220`). Found with a temporary diagnostic patch of H5X_DLL. Fixed by showing only the Skills section in the dialog, whose faction buttons became click buttons without a group (the Heroes and Artifacts sections have groups); `EmptyWindowRectFix` in H5X_DLL gives an empty rect to a window without a Shared, for the saves made before. It used to have one button per faction, each opening an old skill tree of its own (`LevelUpBox/Windows/SkillsLvUp<Faction>`); they were removed.
- The vanilla screen files in `www/UI/*.(WindowScreenShared).xdb` are full copies of the originals with the extra children added. Edit them carefully and keep every vanilla child.

### Root window and tabs

`www/UI/Doc/Root.(WindowSimple).xdb` (the window named `DocRootWindow`, 1280x1024) is a child of each screen that hosts the encyclopedia (adventure map, `CustomGameWait`, `HotSeatWait`, `MPWait`). It is centered horizontally on the screen (`HorAllign` `ERA_CENTER`, x = 79: the visible encyclopedia spans x 40..1082 of the root, so its center is 79 px left of the root's) and 50 px from the top. The level-up box has its own root (see above), not affected.

`www/UI/Doc/Root.(WindowSimpleShared).xdb` lists:

1. The tab buttons `DocTab<Section>.(WindowMSButton)`, from top to bottom Summary, Heroes, Creatures, Skills and Artifacts (their `Position`, 80 px apart, sets the order). They are click buttons: a click runs `<Section>/_Buttons/<Section>Show`, every other `<Other>/_Buttons/<Other>Hide`, enables the other tabs and disables its own (`_Tabs/DocTab<Section>Enable|Disable`, `UI_ENABLE_WINDOW`). The disabled tab is the active one: its `Disabled` sub-state draws the `_Active` bookmark of its texture family (`Bookmark<n>_Active`, `CaravansInfo/Normal` for Summary), like the vanilla Mission Objectives tabs, and it can't be clicked again. The Summary tab starts disabled (`<Enabled>false</Enabled>`), since its section is the one shown on opening. The commands are in the instance's `CommandsOnEnterState`: in the Shared `VisualOnEnterState`, as before, they also ran on a right click, which should only show the tooltip. The tabs (priority 999) stay below the section windows (1000), so the parchment covers their right edge; an active tab drawn above it was tried, and its colors didn't match the parchment's.
2. The section windows `<Section>/<Section>.(WindowSimple)`. They are hidden by default and their names match the Show and Hide messages.
3. The `Close` button.

| Section | Folder | Status | Built by |
|---------|--------|--------|----------|
| Summary | `www/UI/Doc/Summary` | Active | Hand-made |
| Heroes | `www-heroes/UI/Doc/Heroes` | Active | Hand-made structure + `generate-heroes-ui.py` |
| Skills | `www-skills/UI/Doc/Skills` | Active | Hand-made structure + `generate-skills-ui.py` |
| Artifacts | `www-artifacts/UI/Doc/Artifacts` | Active, not yet tested in game | Hand-made `Common/` + `generate-artifacts-ui.py` |
| Creatures | `www-creatures/UI/Doc/Creatures` | Active, not yet tested in game | Hand-made `Common/` + `generate-creatures-ui.py` |

**To add a section:**

1. Create `<Section>/<Section>.(WindowSimple|WindowSimpleShared).xdb` and `<Section>/_Buttons/<Section>Show|Hide.(UISSendUIMessage).xdb`.
2. Create `DocTab<Section>.(WindowMSButton|WindowMSButtonShared).xdb` and `DocTab<Section>.txt` in `www/UI/Doc/`.
3. Add both the tab and the window to `Root.(WindowSimpleShared).xdb`.
4. Add `<Section>Hide` and the new tab's Enable message to the `CommandsOnEnterState` of **every other tab**, write the new tab's `_Tabs/` messages, and give it the other tabs' Hide and Enable messages and its own Disable.

### Faction pattern (Heroes and Skills)

The Heroes and Skills sections follow the same layout:

```
<Section>/
├── <Section>.(WindowSimple|WindowSimpleShared).xdb   # lists the <Faction>Button buttons and the faction windows
├── <Faction>Button/
│   ├── Button.(WindowMSButton|WindowMSButtonShared).xdb
│   └── SwitchOn|SwitchOff.(UISSendUIMessage).xdb      # show/hide the faction window
├── <Faction>/                                         # one faction window
├── Common/                                            # shared textures, formats, labels
└── _Buttons/                                          # <Section>Show|Hide messages, shared button visuals
```

Faction folder names are `Haven`, `Inferno`, `Necro`, `Preserve`, `Dungeon`, `Academy`, `Fortress`, `Stronghold` and `Neutral`. Some differ from the mechanics folder names (`Dwarves` becomes `Fortress`, `Necropolis` becomes `Necro`).

## Generators (`tools/generators/`)

- Requirements: Python 3, `jinja2` and `xmltodict`.
- The generators can be run from any folder, because every path is resolved from `common.py`.
- Every generator accepts two options. `--dry-run` renders everything but writes no file. `--debug` prints details.
- `common.py` holds the shared code:
  - `Generator` writes rendered templates as UTF-8 with CRLF line endings, writes UTF-16 game texts, and prunes stale files.
  - `find_icon_size()` (heuristic) and `texture_size()` (reads a texture's `Width`) give icon sizes.
  - Helpers for paths and xmltodict: `as_list`, `items`, `href_path`, `game_path`. **Use `game_path()` for in-game paths, never `os.path.join`.** On Windows, `os.path.join` inserts backslashes.
- Templates are named `<component>.(<Type>).xdb.j2` and live in `templates-heroes/`, `templates-skills/`, `templates-artifacts/` and `templates-creatures/`.
- Generated files are **overwritten on every run**, and stale numbered files are **removed**. To change a generated file, change its template or the generator, never the output.
- Run `check-ui-refs.py` after any change to the encyclopedia. It reports every `/UI/Doc` href that doesn't resolve in the merged paks, and every show/enable message whose target window name doesn't exist.

```bash
python tools/generators/generate-heroes-ui.py
python tools/generators/generate-skills-ui.py
python tools/generators/generate-artifacts-ui.py
python tools/generators/generate-creatures-ui.py
python tools/generators/check-ui-refs.py
```

A clean run of the heroes or skills generator on unchanged data produces no git diff. Use that to check your own changes to a generator: run it and review `git diff`.

### Heroes (`generate-heroes-ui.py`)

**Inputs:**

- `game_data/heroes/MapObjects/<Faction>/*.xdb`: hero files whose root is `AdvMapHeroShared`, in Explorer order (sorted case-insensitively). Other files are skipped.
- `HeroClass.xdb`, `Skills.xdb`, `UndividedSpells.xdb`, and `Creatures.xdb` together with each creature's visual file.
- `game_data/lua/scripts/game/heroes.lua`: maps hero IDs to their `H_*` Lua constants.
- `game_data/lua/scripts/advmap/handlers/starting-armies.lua`: starting armies. A faction default is used when the hero has no entry.

**Output**, in `www-heroes/UI/Doc/Heroes/`:

| File(s) | Content |
|---------|---------|
| `<Faction>/Heroes.(WindowSimpleShared)` | List of the faction's hero buttons |
| `<Faction>/0000NN.(WindowSimpleShared)` | Faction window (`DocHeroes<Faction>`), listing every hero window |
| `<Faction>/<HeroID>/<HeroID>.(WindowMSButton\|WindowMSButtonShared\|BackgroundSimpleScallingTexture)` | Portrait button in the faction's hero list |
| `<Faction>/<HeroID>/SwitchOn` / `SwitchOff` | Show and hide `Window<HeroID>` |
| `<Faction>/<HeroID>/<HeroID>.(WindowSimple\|WindowSimpleShared)` | Hero window that contains the panels below |
| `<HeroID>/class/` | Name, class, and the four attribute **growth probabilities** of the class (`AttributeProbs`, not starting stats), placed at x = 0/80/160/240 |
| `<HeroID>/army/` | Hero face, plus up to **5 slots in total** for creatures and then war machines, with count texts for creatures only |
| `<HeroID>/spec/` | Specialization text |
| `<HeroID>/skills/` | Skills (with mastery) and then perks, **10 icons at most** |
| `<HeroID>/spells/` | Starting spells, **10 icons at most** on two rows |
| `_Skills/`, `_Creatures/`, `_Spells/` | One shared icon per unique ID |
| `www/UI/Doc/Common/N/<n>.txt` | Creature count numbers (in the **www** pak) |

**Hand-made:** the `<Faction>Button/`, `Common/` and `_Buttons/` folders, the `<Faction>/0000NN.(WindowSimple)` and `<Faction>/Heroes.(WindowSimple)` instances, and the `Heroes.(WindowSimple|WindowSimpleShared)` files at the section root.

**Limits and quirks:**

- A faction can have at most 12 heroes (`button_pos`). Beyond any limit, the generator prints a `WARN:` and leaves the extra elements out.
- The `Neutral` faction is commented out in `factions`.
- `CREATURE_ARCANE_EAGLE` is displayed as `CREATURE_SNOW_APE`.
- Spells always use a 128px texture shown at 64px. Skill and perk icons are sized by `find_icon_size()` (64 or 128), because H5A textures live in vanilla paks with mixed sizes. When you add an icon texture whose size differs from the default, update that function in `common.py`.

### Skills (`generate-skills-ui.py`)

**Element IDs** are 6 digits: the skill's 3-digit index in `Skills.xdb`, then the 3-digit rank. The rank is `001` to `004` for skill masteries and `000` for perks. The build layout also uses `<skill index>000` for the description of a skill itself (`skill_description()`), which can't collide since a skill's index is never a perk's. For example, `001001` is Logistics Basic and `019000` is the first perk with index 19.

**The folder layout drives generation.** A skill is only generated if the folder `www-skills/UI/Doc/Skills/_Skills/<Branch>/<ID>/` already exists. The branch folder determines which tree the skill appears in. If an ID has no folder, the generator prints `WARN: missing button folder`. This is expected for the unused IDs (`HERO_SKILL_<n>`, `Innates`, and so on).

**To add a skill or perk to the tree:**

1. Create the empty folder `_Skills/<Branch>/<ID>/`.
2. Add its position to `coordinates_skills` as `at("<Branch>", dx, dy)`. These are positions in the former trees, which still order the build layout. The masteries are at y=5 and the perks at y=45, with x steps of 25: the x orders the perks of a chain, and the y orders same-depth alternatives (35 and 55 when stacked). In `Innates` and the racial branches, y=26 is an innate perk and y=68 an ultimate. A missing entry is reported with a `WARN:`.
3. Run the generator. It also refreshes the description list.

**Output:**

- Per element, in `_Skills/<Branch>/<ID>/`: its icon, `<ID>.(BackgroundSimpleScallingTexture)`. In `gray/`, the gray icon of a basic mastery, only for the skills that a class view grays out (`gray_icon()`).
- Per element, in `_Description/<ID>/`:
  - The description window `Window<ID>`.
  - The icon, name and description text views.
- `_Description/000000.(WindowSimpleShared).xdb`: the list of every description window. Description folders of elements that are no longer displayed are removed.
- Each run removes every other file of `_Skills` (the files of the former trees, or of elements no longer displayed). The element folders are kept, because they place the elements.
- `branch_extra` adds elements of another branch to a racial skill's innates. For example, Spiritism shows BloodRage's `176000`.

**Prerequisites** are computed from `Skills.xdb` (`BasicSkillID`, `SkillPrerequisites`). In the tree panel, hovering an element highlights each element it requires (`requirements()`).

**Variants:** `DestructiveMagic` and `NaturalMagic` exist as `_a` to `_d` folders, because their 4 elemental perks are ordered differently per faction (`variant_element_y`). An element shared by the variants is expected in all of them. Each faction uses one variant letter, set in `factions`.

**Gray icons:** a gray icon is a plain `WindowSimple` (the grid's `Gray.(WindowSimple)` instance gives it the skill name as tooltip), so it can't be hovered for a description or clicked.
- The gray texture is the perk's `Texture/Item[0]` (`*_grey`) in `Skills.xdb`. Otherwise it's `<icon>_grey.xdb` or `<icon>_grey.(Texture).xdb` at the icon's path, in any data folder. Without either, the normal icon is drawn with a gray `<Color>` tint (`gray_tint`). 12 basic masteries have no gray texture. `--debug` lists them with their icon paths.

**Class views:** each faction window has a Might and a Magic button. These are click buttons, generated with their `<Kind>Enable` / `<Kind>Disable` messages.
- A view shows `DocBuild<Faction>` and its class layout, and hides the other class's. Its skills are those of the class (`HeroClass.xdb` → `SkillsProbs` with `Prob > 0`).
- The selected view button is disabled, which shows it highlighted.
- The view then selects its racial skill (`build_default`).
- The faction buttons (`<Faction>Button/Button.(WindowMSButton|Shared)`) are generated too, in a row (`faction_button_x`, `faction_button_step`). They are click buttons without a button group (see the level-up box): selecting a faction shows its faction window (`SwitchOn`), its layout on its Might view (the first of `class_kinds`) and a glow behind its button (`<Faction>Button/Sel`, `DocSkillsSel<Faction>`, like the skills of the layout), and hides the other factions' ones. Their tooltips are the vanilla faction names (`/GameMechanics/RefTables/<Faction>.txt`).

**Build layout (every faction, and Neutral):** two panels per class, generated in `<Faction>/Build/<Kind>/`. The layout (`build_area`) starts at x=70 in the skills window.
- **Center:** the faction texture `<Faction>/<Faction>.(Texture).xdb` (hand-made, one per faction) is the backdrop of the racial row and the grid (`grid_back_box`, 581x242, ending at the description backdrop). Its picture is 648x241 (`grid_back_picture`); some textures pad it to 1024x256 (Fortress, Stronghold), and since the whole texture is scaled to its window, the window is enlarged by the texture/picture ratio. The basic skill icons are in the 2x8 grid of `build_grid`, centered in it, whose top was aligned with the top of the old description scroll (`grid_top`, y=250 in the skills window). Training and Despotism have their own slots; Sorcery and Voice still share one, which shows the class's own branch, else the other class's, else the first one. The racial skill of the class (Stronghold's Might class has Blood Rage, its Magic class Spiritism) is on a row above the grid: centered on it, 64x64 (`racial_icon_size`) in an 80x80 frame (`Common/Racial`, hand-made, `racial_back_size`), and raised above the row (`racial_raise`) so that the frame sits on the top border of the grid backdrop. Its innate perks (the information perks of the tree, with the `branch_extra` elements of the branch: Spiritism shows Blood Rage's Orcish Fury; Home Land and Retribution for Haven), innate before ultimate (their old row), are aligned right with the grid (`innate_step`); they are only hovered and are left out of the tree. Each innate has a label on its left, 60px wide so that it doesn't cover the previous perk, "Innate" or "Ultimate" from its row in the old Innates column (y=26 or 68), in `Common/InnateLabel`: the gold format of the artifact set labels (`SetLabel`), aligned right. The class's skills are buttons: clicking one shows its tree below and its selection glow (`<Skill>/Sel`), and hides the others'. The other skills are gray icons (`Gray.(WindowSimple)`, using the element's `gray/` icon) with the skill name as tooltip, and can't be clicked. Left of the racial skill, a class view has its title on two lines (`Title<Label|Name>`, `class_title_size`): "Hero class" (`Common/ClassLabel.txt`, UI-local, so not translated) above the class name (the `NameFileRef` of `HeroClass.xdb`), in h3 (`Common/ClassTitle`, Header font, 22px). h2 (28px) or a single line don't fit "Hero class Mountain Lord" in that space, and the title must be larger than the innate labels (body, 18px). Neutral has no title.
- **Tree (bottom):** below the grid backdrop, without a backdrop, down to y=675 in the skills window (`description_bottom`, the bottom of the old description scroll). The masteries are centered on top, and the perks are right below them, in the horizontal order of the old trees: the 2 perk chains of the skill run from left to right by depth, in the left and right halves (3 columns each). Same-depth alternatives are stacked in their column in the order of their rows in the old trees (`variant_element_y` for the elemental perks), which keeps a perk on the line of its requirement (Blaze Power and Ignite). Every tree is laid out as if its columns had 3 stacked perks (`tree_stack`), so a single perk is always on the middle line, the one of Destruction Learning, even in a tree on one line like Offence. The information perks without a mastery requirement are on a row below them. When they don't fit, the generator prints a `WARN:`. Tree elements are only hovered: hovering one highlights its requirements (`requirements()`, built on `prerequisites`) and shows its description.

Every skill icon of the layout is 48x48 (`build_icon_size`). Each view also selects its first skill, the racial one, so its tree is open when landing on the view. The faction window holds only its view buttons (`view_button_x`, `view_button_y`). It is moved by hand between the faction buttons and the exit button (726,50, 137x81), above the build area: the build window is drawn above the faction window and would catch clicks where they overlap. The faction windows are hidden by default and shown by their faction button (`SwitchOn`): all at the same place, they were all visible until a faction button released another, so the Neutral view showed the view buttons of a class faction. Every button of the layout is a click button that draws its icon as a background (`write_click_button`). `DocBuild<Faction>` has priority 10 (`build_priority`), above the windows that overlap it at priority 0 (the faction window, and the containers of the former trees), which caught its clicks otherwise. Hovering any skill or element shows its description in the right panel. The skills of the center show the description of the skill itself, not of its basic mastery: the name and description of its texts folder `0` (`Text/Game/Skills/Unique/Courage/0/`, next to the masteries' `1` to `4`), which `Skills.xdb` doesn't reference, with the icon of the basic mastery. The selected skill is shown by a glow behind its button (`Common/Highlight`, additive, `selection_padding` larger than the button), not by disabling the button as the view buttons are: a disabled button never reverses its `MouseOver` commands, so its description stayed shown and piled up with the next ones, even with a hide in the click and in the `Disabled` sub-state. The center is drawn in 4 layers: the grid backdrop (priority 0), the racial frames (1), the selection glows (2), then the icons and labels (3).

A hero build tracker (a bar listing the picked skills and perks) was tried and dropped: the UI can only show, hide, enable and disable windows by name, so it can't put an element in "the next free slot", count perks or check a limit.

**Neutral** has no classes, so it has a single view, `Neutral/Build/All/`, without view buttons, where every skill of the grid can be selected (elemental variant `c`, Sorcery in the Sorcery/Voice slot). Its faction skill is Innates (`HERO_SKILL_INNATES`, `innates_basic`): it has no element folder, so its icon is generated in `Neutral/Build/InnatesIcon`, and its description uses its texts `Text/Game/Skills/Innates/`. Its tree shows the 14 perks of the old Innates branch in balanced rows (a tree without masteries nor chains), instead of putting them beside it. the Neutral window lists nothing.

Window names are `DocBuild<Faction><Kind><What><ID>`. Selecting a faction hides the other factions' `DocBuild<Faction>`. Each faction's `Build/Build.(WindowSimple)` must be listed by hand in `Skills.(WindowSimpleShared)`. Despotism has a single perk chain, so the generator warns that its perks are not 2 separate chains; its tree only fills the left half. The former trees (branch windows, gray branches and their messages, the `_Skills/Common` and `_Skills/Gray` containers) were removed once the level-up box opened the encyclopedia instead of its own trees.

**Hand-made:**

- Faction windows (`<Faction>/<Faction>.(WindowSimpleShared)`), which list only the view buttons (none for Neutral), and are moved beside the faction buttons.
- The faction window messages (`<Faction>Button/SwitchOn|SwitchOff`).
- `Common/`, `_Buttons/`, `Skills.(WindowSimpleShared)` (it lists the faction buttons, their `Sel` glows, the faction windows and the `Build` windows), and the `LevelUpBox` overrides.
- The description backdrop `_Description/DescriptionBack` (656,150, 435x870). Behind the description text, `_Description/DescriptionInner` (`WindowDescriptionInner`, 682,202, 387x738, priority 200, between the backdrop and the text) draws the `TextBack` panel (the frame of `HeroSpecBack`), which covers the top-left 590x577 of its 1024x1024 texture, around the description list, for readability. It is hidden, and shown only with a description: every hover that shows one also runs `_Description/InnerShow` (generated, `description_hover()`), reversed when the mouse leaves. Its scroll texture covers only the top-left 328x602 of 512x1024, and the whole texture is scaled to the window, so the window is larger than the visible scroll (279x512), which must contain the description list `000000.(WindowSimple)` (690,210, 200x400).

### Artifacts (`generate-artifacts-ui.py`)

**Inputs:** `artifacts/.../Artifacts.xdb` and the sets in `core/GameMechanics/RPGStats/DefaultStats.xdb`. Only equipable artifacts with an icon are kept, and not the ones with `CanBeGeneratedToSell` set to `false` (quest, campaign and similar artifacts). Only sets with a `NameFileRef` and at least one shown artifact are kept.

**Navigation** (same pattern as factions and heroes):

1. Three view buttons, `<View>Button/Button` (`ByClass`, `BySlot`, `BySet`), toggle the view windows `DocArtifacts<View>`.
2. Each view window lists one button per category, `<View>/<category>/Button`, and the hidden category windows `DocArtifacts<View><category>`. Categories are the classes, the slots (in `slot_texts` order) and the sets (in `DefaultStats` order).
3. A category window holds a grid of icon buttons, the same in every view: `grid_columns` (9) square cells across the 600px of the window, each with a 48px icon (`grid_icon_size`) centered in it. A cell gets shorter only when the rows don't fit in the window, and the generator warns when a row is shorter than an icon (`grid_cell()`). Hovering an icon shows its description window `DocArtifactsDesc<ID>`, using a reversible `MouseOver` command as in the skill trees.
4. A set category window also has `Panel`: the set name, its description, and one column per bonus tier. A tier starts where the text in `CombinedDescriptionsFileRefs` changes.

**Output**, in `www-artifacts/UI/Doc/Artifacts/`:

| File(s) | Content |
|---------|---------|
| `Artifacts.(WindowSimpleShared)` | Main window: the view buttons, the view windows and the description panel |
| `<View>Button/` | View button, `SwitchOn`/`SwitchOff`, and its UI-local label `Name.txt` |
| `<View>/<View>.(WindowSimple\|Shared)` | View window |
| `<View>/<category>.(WindowSimple\|Shared)` | Category window |
| `<View>/<category>/` | Category button, its switches, and one `<ID>.(WindowMSButton)` icon per artifact. Set categories also have the `Panel`. |
| `ByClass/<category>/Name.txt`, `BySet/Pieces<n>.txt` | UI-local labels. Slot labels are the vanilla `/UI/HeroScreen3/Inventory/*.txt` texts, and set labels are the set names. |
| `_Artifacts/<ID>.*` | Icon texture (size read with `texture_size()`), icon button visuals (shared by all views), and the icon window of the description |
| `_Description/` | `Back` (the `Common/DescriptionBack` texture), `Descriptions` (list of all descriptions), and `<ID>/` (icon, name, description and set name) |
| `_Description/Formats/` | `Name<Class>.(TextFormat)` and its `.txt`: the `Common/Name` format with the color of the class names in the game, the `<color=...>` tag of `Text/Tooltips/Artifacts/Art<Class>Name.txt` (`class_name_formats()`). The name of a description uses its artifact's class format; Grail, which has no such text, keeps `Common/Name`. |

**Window names** (all unique): `DocArtifactsButton<View>[<category>]`, `DocArtifacts<View>[<category>]`, `DocArtifactsIcon<View><ID>`, `DocArtifactsDesc<ID>[...]` and `DocArtifactsSet<category>...`.

**Hand-made:** `Artifacts.(WindowSimple)`, `_Buttons/` and `Common/`. `Common/` holds the text formats, the shared text view, the icon highlight and the description backdrop `DescriptionBack`, a copy of the old skills one, so that changing the skills backdrop doesn't change the artifacts tab. Every other file is generated, and `Generator.prune_unwritten()` removes the files that the current data no longer produces.

**Cross-pak textures:** the set panel backdrop (`HeroSpecBack`) comes from `www-heroes`.

### Creatures (`generate-creatures-ui.py`)

**Inputs:** `creatures/.../Creatures.xdb` with each creature's file and visual (name, `Icon128`), `CombatAbilities.xdb` (ability names) and `UndividedSpells.xdb` (spell icons and names). Only the creatures of the 9 faction folders of `GameMechanics/Creature/Creatures/` are kept (`factions`: `Dwarf` is Fortress, `Orcs` Stronghold, `Neutrals` Neutral); the others (`_NCF`, `_Darkstorm`...) are left out. Relative hrefs of the data files are resolved against their folder (`resolve()`): the rune names are relative.

**Layout:** two creatures side by side. The central panel (`Panel/`, `panel_box`) has a column of stat icons (`stat_rows`, then Spells and Abilities, icons hand-made in `Common/Stats/<key>`), the stats of the left creature on its left and the ones of the right creature on its right (`column_width`, 170 px). The values are aligned towards the icons, 30 px away from them (`value_gap`): to the right on the left side (`ValueRight`), to the left on the right side (`ValueLeft`). Everything in a column is aligned the same way: the creature icon, its name (`NameRight`/`NameLeft`), the spells and the abilities (`AbilityRight`/`AbilityLeft`); the formats of a side are named by `side_align`. The panel is 380 px wide, and its height follows the content (`panel_box`): it ends just above the bottom of the parchment, so the rows can't grow without shrinking something else. Each side has:
- A row of faction buttons (`<Side>/Factions/`, `DocCreaturesFactions<Side>`). Both rows are at the same place, the faction buttons of the Skills tab: only one is shown, chosen by the two side buttons on top of the panel (`Side/`, the vanilla JogDial arrows, `DocCreaturesSide<Side>`), with a glow behind the selected one (`DocCreaturesSideSel<Side>`).
- A creature grid per faction (`<Side>/<Faction>/Grid`, `DocCreaturesGrid<Side><Faction>`), left or right of the panel: 7 rows of 3 cells, a tier per row with its base creature then its upgrades in the order of its `Upgrades` list. A base creature is one that is not in another creature's `Upgrades`: the `Upgrade` flag is false for some third-line upgrades (`Inferno/3rd/`). The 21 neutrals are in the order of `neutral_order` (rows of 3); a neutral missing from it is shown last, with a warning. A faction button shows its grid and its glow and hides the other factions' ones.
- Clicking a creature shows its stats column `DocCreaturesStats<Side><ID>` and its glow `DocCreaturesGlow<Side><ID>`, and hides the other creatures' ones. To keep a click at about 60 commands (not 189 per creature), the columns and glows are grouped per faction (`DocCreaturesColumn<Side><Faction>`, `DocCreaturesGlows<Side><Faction>`): a click hides the columns and glows of its faction's other creatures, and the other factions' groups, which keep their last selection hidden inside them. The broadcast of a game message (see above) was not used: it was never proven, and it is an adventure reaction that may not run in the lobby screens.

Defaults: the left side is selected, both grids show Haven, no creature is selected.

**Stats column** (`_Stats/<ID>/Stats<Side>.(WindowSimpleShared)`, one per side): the creature icon (48 px, the grid icon texture), its name (one line: 16 characters at most), tier, weekly growth, cost, then after a space (`row_space`) health, attack, defense, damage, shots (`Range` icon), speed, initiative and mana, then the spell icons (one row of 4 at most, 32 px, the spell name as tooltip; creatures know 3 at most) and the ability names (8 at most, the ability description as tooltip, `DescriptionFileRef` of `CombatAbilities.xdb`). Every window of a column is per side (`_Stats/<ID>/<Side>/`). Values are UI-local texts shared by equal values (`_Values/<value>.txt`, `-` is `None.txt`). A cost with resources shows the count and an icon per resource (`/UI/Common/Resources/`; the Phoenix costs 1 of 4 resources). On the left side the icons end where the values end, after the text. On the right side they follow the text at a fixed offset (`cost_text_width`, an estimate of the width of "5000 + 1": every cost with resources has 4 digits of gold), to adjust if the icons overlap the text or are too far from it in game. Spells without an icon (`SPELL_ABILITY_*`, abilities cast as spells, also in the abilities) and the runes of the Fortress rune mages (`SPELL_RUNE_*`, 10 each) are left out.

**Output**, in `www-creatures/UI/Doc/Creatures/`: `Creatures.(WindowSimpleShared)`, `Panel/`, `Side/`, `L/` and `R/` (faction rows, then per faction its grid, glows, columns and their messages), and the files shared by both sides: `_Factions/` (button visuals), `_Creatures/` (icons and button visuals), `_Frames/` (the 21 cell frames, with the hand-made `Common/Creature_back` Shared), `_Stats/`, `_Spells/`, `_Resources/` and `_Values/`. About 11400 files.

**Hand-made:** `Creatures.(WindowSimple)`, `_Buttons/` and `Common/`: the stat icons `Common/Stats/<key>.(BackgroundSimpleScallingTexture)`, the panel texture `Common/Stats/_Holder`, the cell frame `Creature_back`, the text view Shared `Text`, the formats `NameRight`, `NameLeft`, `ValueRight`, `ValueLeft`, `AbilityRight` and `AbilityLeft` (the centered `Name`, `Value` and `Ability` are no longer used), and the UI-local labels (stat tooltips, `Neutral`, `SideL`, `SideR`). The `Common/Stats/*.(WindowSimple|WindowSimpleShared)` files are left from the prototype and are no longer referenced. The selection glows use the Skills tab's `Common/Highlight` (www-skills).

## Workflow checklist

1. **Change the source data first**: the mechanics `.xdb` files, the Lua starting armies, or the English texts.
2. **Generated parts**: edit the generator or template, run it, read the `WARN:` and `Remove stale` lines it prints, and review `git diff`.
3. **Hand-made parts**: copy an existing sibling file of the same type, then adjust `Name`, `Shared`, `Placement` and the hrefs. Register the element in its parent's Shared `<Children>`, and wire its show and hide commands.
4. **Check the references**: run `python tools/generators/check-ui-refs.py`.
5. **Sync every touched pak** (`sync-www*.ps1`, `sync-hud.ps1`), then test in game: open the encyclopedia, switch tabs and factions, and hover icons.
